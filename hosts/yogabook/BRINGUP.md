# Lenovo Yoga Slim 7 14Q8Y11 (`83QR`) — Kalambo / Mahua Bring-Up Status & Handoff

Host `yogabook` (`aarch64-linux`, Snapdragon X2 Plus `X2P-42-100` — upstream codename **Kalambo**, 6-core Cluster 1 `cpu6..cpu11` derivative of Mahua/Glymur).
This file tracks verified hardware state, applied fixes, post-reboot checks, and critical invariants.

## Kernel & Packaging Architecture

`yogabook` does **not** depend on a separate kernel fork repo. The Nix flake is self-contained:

- `pkgs/linux-mahua/default.nix` — fetches upstream `torvalds/linux` `7.4-rc3` (`7b7fe306dd86b5342d3be8a3f1cbf3bb1ebf280f`) via `fetchurl`, applies 14 patches (`pkgs/linux-mahua/patches/0001`–`0014`), and pins Kalambo/Mahua Kconfig in `structuredExtraConfig` (including `ARM_SCMI_PROTOCOL=y`, `ARM_SCMI_CPUFREQ=y`, `QCOM_CPUCP_MBOX=y`, `QCOM_PD_MAPPER=y`).
- `pkgs/mesa-mahua/` — scoped Mesa package adding Adreno X2-45 (`0xc144060020`, 2 slices, 10.5 MiB GMEM) support, wired via `hardware.graphics.package` (never override `pkgs.mesa` globally in `overlays/`, which breaks `cache.nixos.org` for all GUI packages).
- `overlays/mahua-kernel.nix` — exposes `pkgs.linuxPackages_mahua` and `pkgs.alsa-ucm-conf-mahua` (never override global `alsa-ucm-conf`!) with the `Lenovo-Yoga-Slim7-14Q8Y11` UCM2 profile (`2x WSA8845` speakers, `2x VA DMICs` with `CaptureChannels 2`, `2x DP audio` priority `80` **below** `Speaker`'s `200` so a plugged-in USB-C monitor never steals the default sink) plus the exact `LENOVO-83QR-YogaSlim714Q8Y11-LNVNB161216.conf` CardLongName symlink required by ALSA UCM2 / PipeWire. The `DISPLAY_PORT_RX_0/1 Audio Mixer MultiMedia3/4` csets **must** stay in `SectionVerb.EnableSequence` (with no `EnableSequence`/`DisableSequence` left in the `HDMI0`/`HDMI1` `SectionDevice`s): PipeWire's ACP profile probe opens every advertised PCM (`hw:0,0..3`) *before* enabling any `SectionDevice`, so device-level DP routing makes the probe reject the whole verb and the card exposes only `off`/`pro-audio` (zero sinks/sources). The accepted cost is that an idle DP front-end can log `Failed to start APM port 129` on the ADSP — cosmetic, unlike a missing `HiFi` profile.
- `hosts/yogabook/hardware-configuration.nix` — **initrd is display-free** ("Option A", built and awaiting first reboot verification): `boot.initrd.kernelModules = [ "i2c_hid_of" "hid_multitouch" ]` only, and the display stack moved to `boot.kernelModules = [ "mdt_loader" "phy_qcom_qmp_combo" "aux_bridge" "aux_hpd_bridge" "drm_dp_aux_bus" "drm_display_helper" "panel_samsung_atna33xc20" "msm" ]` (stage 2). `boot.initrd.availableKernelModules` keeps everything stage 1 needs for LUKS + FIDO2 + NVMe + I2C keyboard (`xhci_pci`, `nvme`, `usb_storage`, `sd_mod`, `usbhid`, `i2c_hid_of`, `i2c_hid_of_elan`, `hid_multitouch`) plus `phy_qcom_qmp_combo` — that one is **not** display: `usb_0_qmpphy` (`qcom,glymur-qmp-usb3-dp-phy`) is only driven by `phy-qcom-qmp-combo` (=m) and `dwc3_core_get_phy()` does `devm_phy_get(dev, "usb3-phy")` (-EPROBE_DEFER if unbound), so without it the DWC3 controllers (incl. `a600000.usb`, the YubiKey port) never probe in stage 1. `simpledrm` is built into the kernel Image (`CONFIG_DRM_SIMPLEDRM=y`), and `usbhid`/`xhci-plat-hcd`/`dwc3-qcom` are built-in too. No initrd firmware staging is left: `msm` loads after switch-root, where `mahua-firmware` already ships `qcom/gen80100_{sqe,gmu,aqe}` in `/lib/firmware`. The earlier reserve fallback ("Option A'": `regulator-always-on` on `VREG_EDP_3P3` via a `hardware.deviceTree.overlays` DT overlay) was **confirmed active in the booted DT, still produced a visually black LUKS prompt, proven a Stage-1 no-op, and has been dropped** — see the Display bullet below.
- `hosts/yogabook/firmware/` — every proprietary Lenovo 83QR blob (23 files: Adreno `qcom/gen80100_*`, ADSP/CDSP `qcom/glymur/LENOVO/83QR/*`, the `Lenovo-Yoga-Slim7-14Q8Y11-tplg.bin` topology, WCN7850 `ath12k/WCN7850/hw2.0/*` and BT NV `qca/hmtnv20.*` + `qca/hmtbtfw20.tlv`) is **git-tracked and wired declaratively**: `configuration.nix` builds a local `runCommandLocal "mahua-firmware"` (with `compressFirmware = false`, `meta.priority = 1`) and adds it to `hardware.firmware`, so a fresh install has everything in `/lib/firmware` with no manual copying. Uncompressed is required: the kernel tries the plain name before `"$name.zst"` (so these win over `linux-firmware`'s `.zst` siblings without `buildEnv` collisions), userspace `pd-mapper`/`tqftpserv` open `.jsn`/`.mbn` directly, and initrd's `makeModulesClosure` copies by plain name. `regulatory.db`/`regulatory.db.p7s` are *not* vendored — `hardware.wirelessRegulatoryDatabase` (implied by `enableRedistributableFirmware`) ships `pkgs.wireless-regdb`.
- `hosts/yogabook/configuration.nix` — wires `boot.kernelPackages = pkgs.linuxPackages_mahua`, `hardware.deviceTree.name = "qcom/mahua-lenovo-yoga-slim7-14q8y11.dtb"` (with `hardware.deviceTree.overlays = [ ]` — the former `VREG_EDP_3P3` `regulator-always-on` overlay was dropped as a proven no-op), `services.pipewire.wireplumber.extraConfig."51-mahua-no-alsa-suspend"` (ALSA output idle suspend off, see Audio below), `consoleLogLevel = 3`, Kalambo `kernelParams`, the `mahua-firmware` derivation, `s2idle` wakeup rules, `mahua-wakeup-sources`, `mahua-sleep-quirks` (the `sleep.target` unbind/rebind wrapper), `zramSwap.enable`, `upower.criticalPowerAction = "PowerOff"`, and `systemd.sleep.settings.Sleep.SuspendState = "freeze"`. GRUB does **not** read `hardware.deviceTree.name` (`install-grub.pl` ignores it), so the DTB reaches GRUB via `boot.loader.grub.extraFiles` + `extraPerEntryConfig`. `extraPerEntryConfig` uses `devicetree ($drive1)/dtbs/qcom/mahua-lenovo-yoga-slim7-14q8y11.dtb`: `install-grub.pl` substitutes `@bootRoot@` only for the default entry (before `addProfile` runs), so every submenu generation entry used to keep a literal `@bootRoot@` and failed to load the DTB. `boot.loader.grub.configurationLimit = lib.mkForce 8` overrides `modules/core.nix`'s `3` (that is why only 3 generations were listed); `copyKernels` deduplicates by store path, so the shared 70.6 MiB `Image` is stored once and 8 generations cost ~287 MiB of the 786 MiB free on the 1022 MiB ESP.

> **Nix Cache Rule of Thumb:** Never override core shared libraries (`alsa-ucm-conf`, `mesa`, `llvm`, etc.) in `overlays/`. Always scope overrides to dedicated package names (`alsa-ucm-conf-mahua`) or NixOS module options (`hardware.graphics.package`).

## Hardware Fixes Implemented (Linux `7.4.0-rc3`, patches `0001`–`0014`)

- **Display, Backlight & LUKS Console:** Samsung `ATNA40CT03-0` 14.0" 1920×1200@60Hz AMOLED eDP (`panel_samsung_atna33xc20`, eDP v8 PHY patches `0009`–`0010`, backlight patch `0011`). The LUKS/FIDO2 prompt is drawn by `simpledrm` (built-in, `CONFIG_DRM_SIMPLEDRM=y`) on the UEFI GOP-lit panel, which is why the **entire display stack is stage-2 only** (`boot.kernelModules`, not initrd). Root cause of the earlier black prompt: with `msm` + `panel_samsung_atna33xc20` in initrd, `atna33xc20_probe()` runtime-autosuspended ~2 s after probe (dropping `VREG_EDP_3P3` and putting the TCON into DPCD D3) because `msm_dpu` deferred on `af54000`/`af5c000` (`pmic_glink_altmode` is stage-2 only, after ADSP `remoteproc1`), which killed the `simpledrm` scanout. Keeping the display stack in stage 2 preserves both the visible prompt and the reliable post-switch-root `msm_dpu` bring-up. **"Option A'" (`regulator-always-on` on `VREG_EDP_3P3`) was tried and is now dropped.** It was applied as a `hardware.deviceTree.overlays` DT overlay (`&{/regulator-edp-3p3}`, DTB-only via `apply_overlays.py` + libfdt, no kernel/DTS rebuild) and **confirmed live in the booted DT** (`ls /proc/device-tree/regulator-edp-3p3/` listed `regulator-always-on` next to `regulator-boot-on`) — yet the stage-1 LUKS prompt was **still visually black**. It is a Stage-1 **no-op**: the board DTS already sets `regulator-boot-on` on that rail and the cmdline already passes `regulator_ignore_unused`, which is what keeps it up during early boot, so `regulator-always-on` changed nothing there. Its only real effect was *harmful*: it prevents the panel 3.3 V rail from powering down during `s2idle`, adding standby drain. Removed from `hosts/yogabook/configuration.nix` (`hardware.deviceTree.overlays` is now `[ ]`; `enable`/`name` untouched). **Next test (not yet run):** GRUB `e` → append `ignore_loglevel loglevel=8` to distinguish an *empty console* (kernel logging to tty0 but nothing printed / console not bound) from a *dead UEFI GOP scanout* (simpledrm never taking over the framebuffer) — the two have completely different fixes, so this must be resolved before touching any further regulator/panel sequencing.
- **Desktop & GPU:** Hyprland Wayland (`modules/hyprland.nix`, `modules/hyprland-home.nix`) + Adreno X2-45 (`pkgs/mesa-mahua/`) + patch `0013` adding speed-bin `193` (`0xc1`, `915 MHz`, `BIT(4)`) and `opp-supported-hw = <0x1f>` on `310..915 MHz` OPPs.
- **CPU Frequency Scaling (Kalambo SCMI / CPUFreq):** Patch `0012` adds upstream `kalambo.dtsi` (PDP1 mailbox TX at `0x1a980000`, `imem` size `0x380` with `cpu_scp_lpri1` at `@200`, `cpu6..11` reassigned to `<&scmi_perf 0>`, trimmed 19-range `&pdc`). Board DTS (`0008`) includes `kalambo.dtsi` while retaining `"qcom,mahua"` compatible so `7.4-rc3` `qcom_pd_mapper` keeps matching `audio_pd`. Removed `initcall_blacklist=scmi_driver_init,qcom_cpucp_mbox_init`.
- **USB-C UCSI & eUSB2 Repeater:** Replaced `dr_mode = "host"` with `role-switch-default-mode = "host"` on `&usb_0`, `&usb_1`, `&usb_2` in `0008` so DWC3 registers `usb_role_switch` (unblocking `ucsi_glink` `/sys/class/typec/port{0,1,2}` while defaulting to host mode). Added upstream patch `0014` (`a6d71ecf65b3`) disabling `EUSB2_EN_CTL1` on `smb2370` eUSB2 repeater exit to fix SMB power leakage.
- **Audio (PipeWire / ALSA UCM2):** `alsa-ucm-conf-mahua` symlinks `LENOVO-83QR-YogaSlim714Q8Y11-LNVNB161216.conf`, sets `CaptureChannels 2` on internal DMICs, and ranks `Speaker` (`PlaybackPriority 200`) above `HDMI0`/`HDMI1` (`80`). The DP mixer csets (`DISPLAY_PORT_RX_0/1 Audio Mixer MultiMedia3/4`) are **verb-level** (`SectionVerb.EnableSequence`) because PipeWire's ACP profile probe opens every PCM `hw:0,0..3` before enabling any `SectionDevice`: with the routes only in the `HDMI0`/`HDMI1` devices the probe rejected the entire `HiFi` verb and the card exposed only `off`/`pro-audio` (zero sinks/sources, caught on boot 0). Verb-level routing also means the DP front-ends are routed with nothing plugged in, so the ADSP can log `Failed to start APM port 129` for an idle DP port. (Note: 83QR has no 3.5 mm jack in hardware.) **Reproducible ADSP wedge (under investigation):** on both of the last boots the same sequence appears — first `q6apm-dai ... Error queuing playback buffer -16` (`-EBUSY`, the very first playback), then the APM channel never recovers and `qcom-apm gprsvc:service:2:1: CMD timeout for [100100x]` + `q6apm-lpass-dais ... Failed to set media format -110` (`-ETIMEDOUT`) repeat every ~5 s indefinitely (1147 `-110` lines in one 2 h 44 min boot). Playback is dead for the rest of the boot; the DSP-side port/stream state is stuck, not the kernel side. Not cosmetic — needs an ADSP-side (or `q6apm`/`q6apm-dai` reset) fix, not a UCM2 change.
  - **H1 — `q6apm` graph teardown churn → mitigated by `51-mahua-no-alsa-suspend`:** WirePlumber's default 5 s ALSA idle suspend tears the `q6apm` graph down and rebuilds it on every pause/play. `q6apm_dai_prepare()` and `q6apm_graph_close()` ignore APM command errors, so a teardown that races a still-open port silently desyncs host and DSP state — exactly the shape of the observed `-16` → permanent `-110` wedge. `hosts/yogabook/configuration.nix` now sets `services.pipewire.wireplumber.extraConfig."51-mahua-no-alsa-suspend"` with a `monitor.alsa.rules` entry matching `node.name = "~alsa_output.*"` and `update-props { node.pause-on-idle = false; session.suspend-timeout-seconds = 0; }`, i.e. sinks stay running across pauses and the graph is never torn down. This removes one trigger, not the root cause — a graph that wedges while *continuously* playing still needs the `q6apm`/ADSP-side fix.
  - **H2 — `Failed to start APM port 129` is a real hazard, not cosmetic:** this is *not* purely a log line. It means an APM port was left half-started on the DSP: the GPR command did not complete cleanly, so the DSP believes a port/stream is partially open while the host side considers it closed (or vice versa). A later `q6apm_dai_prepare()` on that port is what returns `-16`/`-110`, because the error is never propagated or cleaned up. Treat any `Failed to start APM port ...` as an early warning of the wedge above rather than noise to be filtered, and correlate it with the `-16`/`-110` timestamps before dismissing it.

Verify the unit after a rebuild with `systemctl cat mahua-sleep-quirks` and `/run/mahua-sleep-quirks/` (present only while suspended).

## Battery Life / Runtime PM (Tier 1, applied)

`services.udev.extraRules` in `configuration.nix` enables runtime PM on the four USB controllers that have nothing attached plus their QMP USB3 PHYs. The mapping below is read from `/proc/device-tree/soc@0` (`phys`/`phy-names` phandles) and `/sys`, not assumed:

| Controller | xHCI child | eUSB2 PHY (no runtime PM) | QMP PHY (runtime PM) |
|---|---|---|---|
| `a000000.usb` (peripheral-only UDC role, **but** it does have an xHCI child) | `xhci-hcd.3.auto` → `usb4`, `usb5` | `88e0000.phy` | `88e1000.phy` |
| `a200000.usb` | `xhci-hcd.1.auto` → `usb1` | `fa0000.phy` | — |
| `a400000.usb` | `xhci-hcd.2.auto` → `usb2`, `usb3` | `fa1000.phy`, `fa2000.phy` | `fa3000.phy`, `fa5000.phy` |
| `a800000.usb` | `xhci-hcd.5.auto` → `usb8`, `usb9` | `fdd000.phy` | `fde000.phy` |
| `a600000.usb` — **excluded** | `xhci-hcd.4.auto` → `usb6` (YubiKey at `6-1`), `usb7` | `fd3000.phy` | `fd5000.phy` |

- **The `xhci-hcd.*.auto` exclusion was broken and is fixed:** the rule used to be `... KERNEL=="xhci-hcd.*.auto", KERNELS!="a600000.usb"`, which does **not** exclude anything. `KERNELS`/`ATTRS` walk the device *and* every ancestor, and `!=` is true as soon as any one of them fails to match — `xhci-hcd.4.auto`'s own `KERNEL` is not `a600000.usb`, so the negated match was true and `99-local.rules` wrote `power/control="auto"` to the YubiKey port's xHC (observed live: `xhci-hcd.4.auto` → `auto`, `runtime_status=suspended`, with `udevadm test --action=add` naming `99-local.rules:50 ATTR{power/control}="auto"`). The rule now whitelists the four unused parents positively: `KERNELS=="a000000.usb|a200000.usb|a400000.usb|a800000.usb"`, which is only true when the device or one of its parents really carries that name. Verify with `udevadm test --action=add /sys/devices/platform/soc@0/<parent>.usb/xhci-hcd.<N>.auto`: `ATTR{power/control}="auto"` must appear for `{1,2,3,5}` and must **not** appear for `xhci-hcd.4.auto`.
- **Why `power/control="auto"` is the right knob:** both `dwc3_core_probe()` (`drivers/usb/dwc3/core.c`) and `xhci_plat_probe()` (`drivers/usb/host/xhci-plat.c`) call `pm_runtime_forbid()`, which takes a permanent `usage_count` reference; `pm_runtime_allow()` (what a `"auto"` write does) drops it. Before the write the devices read `power/control=on`, `runtime_enabled=forbidden`, `runtime_usage=1`; the root hubs (`usb1/2/3/4/5/8/9`) are already `auto`/`suspended`, so once the forbid reference is gone the xHCI idles and the glue autosuspends after its 5 s delay, where `dwc3_qcom_suspend()` runs `clk_bulk_disable_unprepare()` + `dwc3_qcom_interconnect_disable()` — that is where the power actually goes.
- **`ACTION=="add|bind"` is required, not decorative:** `mahua-sleep-quirks` unbinds/rebinds every `xhci-hcd.*.auto` around `s2idle`, and every rebind re-runs `xhci_plat_probe()` → `pm_runtime_forbid()`, i.e. `power/control` would silently revert to `on` after the first sleep without the `bind` trigger.
- **The unbind/rebind cycle stays safe:** `__device_release_driver()` (`drivers/base/dd.c`) does `pm_runtime_get_sync(dev)` before `->remove` and `pm_runtime_put_sync(dev)` after, and `xhci_plat_remove()` itself starts with `pm_runtime_get_sync()`. On the system-sleep path `xhci_plat_suspend_common()` resumes a runtime-suspended controller first (`if (pm_runtime_suspended(dev)) pm_runtime_resume(dev);`), so a runtime-suspended xHCI never reaches `xhci_suspend()`.
- **`a600000.usb` is excluded on purpose:** it is the verified zero-fault `s2idle` path (`SID=0x1420`) and hosts the YubiKey. Enable it only as a separate experiment with a full suspend/resume soak.
- **The M31 eUSB2 PHYs are excluded because they cannot do it:** `qcom-m31eusb2-phy` never calls `devm_pm_runtime_enable()`, so they read `power/runtime_enabled=disabled`, `runtime_status=unsupported` — writing `auto` there is a no-op that would only make `power/control` lie.
- **QMP PHYs are safe to autosuspend:** `phy_power_on()` takes a runtime-PM reference on the PHY and `phy_power_off()` drops it (`drivers/phy/phy-core.c`), so a PHY in use by its controller cannot suspend.
- **Userspace:** Waybar `custom/battery` went from `interval = 3` to `10`. Waybar re-execs `exec` on every tick, and the script costs ~40 ms per run (measured) → ~1.3 % of one core at `3`, ~0.4 % at `10`; charge/PD state moves on a minutes timescale. Nothing else in the bar is worth touching: Waybar as a whole used 9 s CPU in 5346 s (~0.17 %).

### Audited and deliberately *not* changed

- **NVMe (`0005:01:00.0`) runtime PM:** `nvme_dev_pm_ops` (`drivers/nvme/host/pci.c`) has **no** `.runtime_suspend`/`.runtime_resume`, and `pci_pm_runtime_suspend()` falls through to `pci_finish_runtime_suspend()` when the driver supplies no callback — i.e. `power/control=auto` would put the controller into D3hot *behind the nvme driver's back*, with no re-init on the way back. It is a no-op today (`runtime_usage=2`) and a latent data-loss hazard the moment that drops. The SSD's real power management is APST, already active (`nvme_core.default_ps_max_latency_us=100000`).
- **`pcie_aspm.policy=powersupersave`:** nothing to gain — `qcom-pcie` already enables L1 + L1SS on both links (`/sys/bus/pci/devices/0004:01:00.0/link/l1_2_aspm=1`, same for the NVMe link) and deliberately clears the L0s capability (`qcom_pcie_clear_aspm_l0s()`); `powersupersave` would only push L0s, which is the half that is turned off on purpose. Policy stays `default`. `ath12k` (`wcn7850 hw2.0`) has `supports_aspm = true` and re-enables ASPM after firmware boot (`ath12k_pci_start()`), so WCN7850 is not the blocker — the root complex is.
- **`misc.vfr`:** does not exist in Hyprland 0.57.2. `hyprctl getoption misc:vfr` → `no such option`, and the string is absent from the binary/man page. There is nothing to enable; a comment in `modules/hyprland-home.nix` records this so it does not get "re-added". `misc.vrr` stays `0` (fixed-refresh OLED).
- **`charge_control_end_threshold`:** `qcom_battmgr` implements and exposes it (`/sys/class/power_supply/qcom-battmgr-bat/charge_control_end_threshold`, currently `0` = no limit, and it is in `is_writeable()`), so an 80 % cap *is* plumbed through `pmic-glink` on Glymur/Mahua. Not enabled — it needs a one-off write to confirm the EC honours it before it becomes declarative.
- **`wsa884x-codec: Parity error detected`:** 4 lines in a 1 h 28 min boot (2 events, both amps, seconds apart), alongside periodic `SWR bus clsh detected` (SoundWire clock-stop on idle, normal). Rare, harmless, no audio dropout, and not something a NixOS option can influence — it needs a `sound/soc/codecs/wsa884x.c` fix (`scp_int1_mask` currently unmasks `SDW_SCP_INT1_BUS_CLASH | SDW_SCP_INT1_PARITY`).

- **`qcom_camss` (MIPI RGB + IR webcam / ToF):** No `glymur`/`mahua` CAMSS DT nodes, no CCI/CSI-2 PHY pipeline, and no sensor support in `7.4-rc3`. Keep blacklisted. Sensor IDs and the CAMSS/CCI blobs must come from Lenovo's **Windows 11 ARM recovery image** (Lenovo DDRS — Driver Recovery/Download Service, `83QR` recovery media) or the **Microsoft Update Catalog** (`qccam*8480` packages), and only become usable once post-7.4 kernel CAMSS/CCI support lands. Lenovo's 83QR support page publishes **no** camera, graphics or chipset drivers (BIOS + diagnostics only), so it cannot be used as the source.
- **ADSP SSC sensors:** No mainline Qualcomm SSC sensor hub driver.

## Post-Reboot Verification Checklist

After `nh os switch .` and rebooting into the new generation:

1. **Stage-1 LUKS prompt + Stage-2 display ("Option A"):** Confirm the LUKS/FIDO2 prompt is **visible** on `simpledrm` during stage 1 (`dmesg | grep -i simpledrm` → `fb0: simpledrmdrmfb`, no `msm`/`atna33xc20` messages before switch-root), then that `msm_dpu` takes over and lights the OLED panel cleanly after unlock. "Option A'" (`regulator-always-on` on `VREG_EDP_3P3` via a DT overlay) **was confirmed live in the booted DT, still gave a visually black LUKS prompt, and has been dropped** as a Stage-1 no-op that only added `s2idle` standby drain — `hardware.deviceTree.overlays` is `[ ]` again. The stage-1 black prompt is an **open bug** and not a verification step that can be assumed to pass. **Next diagnostic step (run by hand, not declaratively):** at the GRUB menu press `e` on the default entry and append `ignore_loglevel loglevel=8` to the `linux` line, then boot — this distinguishes an *empty console* (kernel is alive and printing but nothing reaches the panel) from a *dead UEFI GOP scanout* (`simpledrm` never took over the framebuffer); the two have different fixes. Also verify the rail state from the running system with `cat /sys/kernel/debug/regulator/regulator_summary` (panel on → `VREG_EDP_3P3` `enabled`, and it may now drop while the panel is suspended, which is expected).
2. **CPUFreq / SCMI:**
   ```bash
   dmesg | grep -iE 'scmi|cpucp|cpufreq'
   grep . /sys/devices/system/cpu/cpufreq/policy0/scaling_{driver,governor,cur_freq,available_frequencies}
   ```
   *(If SCMI ever hangs on boot, pick the previous GRUB generation or append `initcall_blacklist=scmi_driver_init,qcom_cpucp_mbox_init` on the GRUB command line.)*
3. **Adreno X2-45 speed-bin 193:**
   ```bash
   dmesg | grep -iE 'adreno|speed-bin|gmu'   # expect no "missing support for speed-bin: 193"
   cat /sys/class/devfreq/3d00000.gpu/available_frequencies
   ```
4. **USB-C UCSI & USB2 devices:**
   ```bash
   ls -la /sys/class/usb_role/ /sys/class/typec/
   dmesg | grep -iE 'ucsi|typec|eusb2|smb2370'
   ```
   Then plug in a USB-C phone/hub/DP monitor to verify Type-C PD/roles and USB2 enumeration.
5. **PipeWire Audio:**
   ```bash
   wpctl status
   # ALSA idle suspend must be off (the H1 mitigation): no sink should report
   # `node.pause-on-idle = true` / suspend after 5 s of silence.
   pw-dump | grep -A2 '"pause-on-idle"'
   # The conf lives in the `wireplumber-configs` store path, not /etc (NixOS
   # wires it through XDG_DATA_DIRS, so read the live file):
   conf=$(systemctl --user show -p Environment wireplumber \
     | sed -n 's/.*XDG_DATA_DIRS=\([^: ]*\).*/\1/p')
   cat "$conf/wireplumber/wireplumber.conf.d/51-mahua-no-alsa-suspend.conf"
   ```
   Then pause and resume playback several times and confirm no `q6apm-dai ... -16` / `qcom-apm ... CMD timeout` / `-110` in `journalctl -k` (see the Audio section for H1/H2).
6. **Suspend (`s2idle`) staged test (run as root):**
   ```bash
   cat /sys/power/mem_sleep   # expect: [s2idle] deep
   cat /sys/power/state       # expect: freeze mem
   # pm_test ladder — every rung must come back on its own:
   echo freezer  > /sys/power/pm_test && echo freeze > /sys/power/state && echo none > /sys/power/pm_test
   echo devices  > /sys/power/pm_test && echo freeze > /sys/power/state && echo none > /sys/power/pm_test
   echo platform > /sys/power/pm_test && echo freeze > /sys/power/state && echo none > /sys/power/pm_test
   # If all three rungs pass cleanly, test real s2idle:
   systemctl suspend
   # After resume: no `SID=0x1420` context fault, no "xHC error in resume"/
   # "Host System Error", Wi-Fi (`wlP4p1s0`) and every USB device back:
   dmesg | grep -iE 'smmu.*fault|xHC error|Host System Error'
   ls /run/mahua-sleep-quirks 2>/dev/null   # must be gone after resume
   systemctl status mahua-sleep-quirks
   ```
   - **`echo freeze`, never `echo mem`:** `freeze` unconditionally means suspend-to-idle. `mem` means "whatever `/sys/power/mem_sleep` currently selects", so a single stray write of `deep` into `mem_sleep` turns the next `echo mem` into PSCI `SYSTEM_SUSPEND`, which Mahua does not support → silent hang with no wake. `freeze` removes that ambiguity, which is why `systemd.sleep.settings.Sleep.SuspendState = "freeze"` is pinned in `configuration.nix` (systemd 262 removed `SuspendMode=`).
   - **`pm_test` ladder semantics:** `freezer` = tasks frozen only; `devices` = every `.suspend`/`.resume` callback runs and then wakes immediately; `platform` = the `dpm_suspend_late()`/`dpm_suspend_noirq()` (and matching `_early`/`_noirq` resume) callbacks also run. Under **`s2idle`** the `platform` rung does **not** run `s2idle_loop()` and never enters the idle domain — `s2idle_enter()`/`domain_ss3` and `qcom,glymur-pdc` TCS programming are skipped entirely, so passing `platform` proves nothing about idle-state entry. The first rung that hangs identifies the layer: hang at `devices` → a driver's suspend callback; hang at `platform` → a late/noirq device callback, **not** `domain_ss3`.
   - **`cpuidle.off=1` A/B test:** if real `s2idle` (not `pm_test`) hangs, reboot with `cpuidle.off=1` appended in GRUB and repeat. Passing with cpuidle off pins the fault on `domain_ss3`/`qcom,glymur-pdc` idle-state entry rather than a driver callback.
   - **`rtcwake` / timed wake cannot work on this board:** `apps_rsc` reports `CONTROL_TCS 0`, so the RSC cannot arm a TCS/RTC wake timer. `rtcwake -m freeze -s 20` will therefore look like a hang until something else wakes the machine.
   - **Wake sources:** `pmic_pwrkey` (`event4`, IRQ 275, `power/wakeup = enabled`) is the real power button (PMIC event, 2 edges per press; `PowerKeyIgnoreInhibited = "yes"` in `services.logind.settings.Login` is set so user-app `block` sleep inhibitors like T3 Code don't refuse explicit power-key presses). Keyboard wake comes through `event3` (`hid-over-i2c 048D:83DB`, wakeup source `0-003a`, GIC `msmgpio` IRQ 236), and lid open through `gpio-keys` (`event0`, TLMM 92). Those three are the only reliable wake sources.
7. **USB runtime PM (Tier 1) and its interaction with `s2idle`:**
   ```bash
   # All four unused controllers + their xHCI children + the four QMP PHYs:
   grep . /sys/bus/platform/devices/{a000000,a200000,a400000,a800000}.usb/power/control
   grep . /sys/bus/platform/devices/xhci-hcd.{1,2,3,5}.auto/power/{control,runtime_status}
   grep . /sys/bus/platform/devices/{88e1000,fa3000,fa5000,fde000}.phy/power/{control,runtime_status}
   # Must stay untouched (YubiKey port):
   grep . /sys/bus/platform/devices/{a600000.usb,xhci-hcd.4.auto,fd5000.phy}/power/control
   ```
   Expected: `auto` on the first three groups, `on` on `a600000`/`xhci-hcd.4.auto`/`fd5000.phy`; `runtime_status` reaches `suspended` on the unused controllers once nothing is plugged in (~5 s after boot). After one `systemctl suspend`/resume cycle the `xhci-hcd.*.auto` values must still be `auto` — that is what the `ACTION=="add|bind"` rule covers, and it is the only thing that keeps runtime PM from being lost on every resume. A YubiKey must still enumerate on `a600000` (`lsusb`, `ykman info`). Cross-check the rule itself without switching: `udevadm test --action=add /sys/devices/platform/soc@0/a600000.usb/xhci-hcd.4.auto` must **not** mention `ATTR{power/control}="auto"` (it did before the `KERNELS!=` → positive-whitelist fix).

## Critical Invariants & Past Dead Ends (Do Not Regress)

1. **`ATNA40CT03-0` OLED Backlight (Patch `0011`):**
   - The Samsung `ATNA40CT03-0` TCON blanks permanently if `drm_edp_backlight_enable()` rewrites `DPCD 0x721` when its value already matches, or if `current_level == 0`.
   - Keep `0011-drm-dp-skip-redundant-backlight-mode-write.patch` and `BACKLIGHT_CLASS_DEVICE = yes`.
2. **In-Kernel `QCOM_PD_MAPPER = yes` & `"qcom,mahua"` Board Compatible:**
   - `QCOM_PD_MAPPER` must stay built-in (`=y`, not `=m`), and `mahua-lenovo-yoga-slim7-14q8y11.dts` must keep `"qcom,mahua"` in its root `compatible` on `7.4-rc3` (`qcom_pd_mapper.c` matches `"qcom,mahua"`, not `"qcom,kalambo"`) so ADSP `audio_pd` service discovery works.
3. **WSA Macro Audio Routing (`-5 EIO` trap):**
   - `WSA WSA RX0 MUX` and `WSA WSA RX1 MUX` must be set to `AIF1_PB` (`Wsa1SpeakerEnableSeq.conf` in `overlays/mahua-kernel.nix`), otherwise playback times out silently with `-5 (EIO)`.
4. **Firmware (declarative, `/lib/firmware`):**
   - Every Lenovo 83QR blob lives in `hosts/yogabook/firmware/` (git-tracked) and is installed to `/lib/firmware` by `hardware.firmware` via the local `mahua-firmware` derivation (`compressFirmware = false`, `meta.priority = 1`). Nothing has to be copied into `/var/lib/mahua-firmware` on a fresh install.
   - `/var/lib/mahua-firmware` remains on the kernel search path (`firmware_class.path`, restored by `system.activationScripts.mahuaFirmware` after `udevd`, which otherwise overwrites it with the Nix store firmware dir) purely as an **optional override** for testing a new blob without a rebuild; when empty the loader falls back to `/lib/firmware`.
   - Keep the blobs **uncompressed**: the kernel tries the plain name before `"$name.zst"`/`"$name.xz"`, so they shadow `linux-firmware`'s `.zst` siblings (`ath12k/WCN7850/hw2.0/*`, `qca/hmtnv20.*`, `qcom/gen80100_*`); `pd-mapper`/`tqftpserv` read `.jsn`/`.mbn` straight from `/lib/firmware`; and initrd's `makeModulesClosure` copies by plain name. `regulatory.db` is *not* vendored — `pkgs.wireless-regdb` provides it.
5. **Mandatory Boot `kernelParams`:**
   - `nokaslr` + `efi=novamap`: required for Qualcomm EL2 UEFI stub.
   - `arm-smmu.disable_bypass=0` + `clk_ignore_unused` + `pd_ignore_unused` + `regulator_ignore_unused`: preserve UEFI-initialized rails/clocks/SMMU mappings during early boot (boot-only, zero suspend impact).
   - `mem_sleep_default=s2idle`: prevents `echo mem` from entering unsupported PSCI `deep` sleep.
   - `modprobe.blacklist=qcom_iris,qcom_camss`: prevents video/camera coldplug hangs.
   - `consoleLogLevel = 3` (NixOS option, emitted as `loglevel=3`): keeps the benign boot-time `qcom-apm ... 1001021` timeout (`KERN_WARNING`) off `/dev/tty1` while everything still lands in `dmesg`/`journalctl`. Do **not** raise it back to the default `4` without a reason.
